# Creating Temporary Environments in GeoLab — Video Script

**Runtime:** ~6:30 (5–7 min target)
**Format:** Screen-capture (terminal + JupyterLab) + narration (voice-over), light motion graphics for titles/lower-thirds/code call-outs
**Audience:** Researchers and educators already using GeoLab who need packages, versions, or setups beyond the default environment
**Source:** [docs.earthscope.org/geolab/advanced-topics/environments/creating-temporary-environments](https://docs.earthscope.org/geolab/advanced-topics/environments/creating-temporary-environments)

|---|---|---|
| 0:00–0:25 | Cold open: a notebook cell running `import seisbench` and throwing `ModuleNotFoundError`. Cut to a researcher's cursor hovering over it, then a quick montage of a terminal typing `pip install`, a spinning cursor, a memory-warning banner. | **VO:** "You're deep into a notebook, and you hit a wall: the package you need isn't in GeoLab's default environment. Maybe it's a specialized tool like seisbench. Maybe you need an exact version to match a paper's results. Installing it by hand, mid-notebook, can eat memory and still leave your setup impossible to reproduce next week. There's a better way." |
| 0:25–0:35 | Title card: **"Creating Temporary Environments in GeoLab"**, EarthScope/GeoLab lockup. | **VO:** "This is how to build a custom, reproducible environment in GeoLab — on demand, for exactly the packages your project needs." |
| 0:35–1:15 | Split screen diagram: left side labeled **"Default Environment"** with a lock icon and "persists across sessions"; right side labeled **"Temporary Environment"** with a clock icon and "resets when you sign out." | **VO:** "GeoLab gives every user a default environment — pre-loaded with common geophysical packages, and it's always there when you log back in. A temporary environment is different: it's a custom workspace you build yourself, during a session, to hold exactly the packages you specify. It's called 'temporary' because it's deleted when you sign out — but that's not a downside. Because you define it in a single file, you can recreate it in seconds, share it with a collaborator, or hand it to a student, and get the exact same setup every time." |
| 1:15–1:45 | On-screen bullet list, one item revealing at a time over a blurred notebook background: "Add a package that isn't pre-installed" / "Pin an exact version" / "Isolate dependencies for one project" / "Share a reproducible setup." | **VO:** "Reach for a temporary environment any time you need a package that isn't pre-installed, need to pin an exact version without disturbing other work, want to isolate a project's dependencies so they can't conflict with anything else, or want a setup you can hand to someone else and know it'll match yours exactly." |
| 1:45–1:55 | Lower third: **"Step 1 — Write an environment.yml file"** | **VO:** "It all starts with one file: environment dot yaml." |
| 1:55–2:55 | Screen capture: JupyterLab file browser → New → Text File → renamed to `environment.yml`. Editor pane fills in line by line, each key briefly highlighted as it's mentioned: `name`, `channels`, `dependencies`, `ipykernel`, the `pip:` block. <br><br>*(On-screen code, built up progressively:)* <pre>name: my_environment<br>channels:<br>&nbsp;&nbsp;- conda-forge<br>dependencies:<br>&nbsp;&nbsp;- python=3.11<br>&nbsp;&nbsp;- ipykernel<br>&nbsp;&nbsp;- numpy<br>&nbsp;&nbsp;- matplotlib<br>&nbsp;&nbsp;- pip:<br>&nbsp;&nbsp;&nbsp;&nbsp;- seisbench</pre> | **VO:** "Give it a name — this is what you'll call the environment later. List your channels; conda-forge is the one you'll want almost every time. Then list your dependencies: the Python version, any conda packages like numpy or matplotlib — and one package you can't skip, ipykernel. Without it, Jupyter has no way to see this environment as a kernel option. If something's only available on PyPI, not conda, add a pip section underneath and list it there — that's how a package like seisbench gets in." |
| 2:55–3:05 | Lower third: **"Step 2 — Build the environment"** | **VO:** "With the file saved, open a terminal." |
| 3:05–3:50 | Screen capture: JupyterLab terminal. Command typed: `conda env create -f environment.yml`. Scrolling dependency-resolution output plays for a few seconds, sped up 4x with a small "4x" badge, ending in a success message. | **VO:** "Run conda env create, pointing it at your file. Conda reads every package you listed and works out a compatible set of versions for all of them — that resolution step is what takes the time here, so don't worry if it runs for a few minutes on a larger environment. When it finishes, your environment exists — but it isn't active yet, and it isn't visible in your notebooks yet either. Two steps left." |
| 3:50–4:35 | Screen capture: terminal. Command `conda activate my_environment` — prompt visibly changes to show `(my_environment)`. Immediately below, command `python -m ipykernel install --user --name my_environment --display-name "Python (my_environment)"` types out and runs. | **VO:** "First, activate it: conda activate, and the environment's name. Watch your terminal prompt — it now shows my_environment, confirming you're inside it. Second, register it as a notebook kernel: python dash m ipykernel install, with a name and a display name. The display name is what you'll actually see and click inside Jupyter, so make it something you'll recognize later." |
| 4:35–4:45 | Lower third: **"Step 3 — Switch your notebook's kernel"** | **VO:** "One more step, and it's inside the notebook itself." |
| 4:45–5:20 | Screen capture: open a notebook, click **Kernel** menu → **Change Kernel…**, dialog shows a list including "Python (my_environment)," click it, then zoom into the kernel indicator in the top-right corner of the notebook updating. | **VO:** "Open your notebook, go to Kernel, then Change Kernel, and pick the display name you just chose. Check the top right corner of the notebook — it now shows your new environment as the active kernel. Keep in mind, this is set per notebook, not project-wide, so if you're using this environment across several notebooks, you'll repeat this last step in each one." |
| 5:20–5:50 | Screen capture: terminal running `%conda install -c conda-forge pandas` and `%pip install earthscope-sdk` directly inside a notebook cell, with output below each. On-screen label: **"Quick, one-off installs"**. | **VO:** "For a single extra package, you don't always need a full environment file — GeoLab also supports installing directly inside a cell, with percent-conda-install or percent-pip-install. It's faster for a one-off package, but it's less reliable for anything large, since it's checking for conflicts live, inside a running notebook." |
| 5:50–6:20 | On-screen warning card, icon-led, three lines appearing in sequence: "Installing with %conda inside a notebook can spike memory — if it hangs, switch to environment.yml." / "No sudo or apt-get — system-level installs need a custom image." / "Pip won't resolve conflicts for you — read the error, adjust the file." | **VO:** "A few things to watch for. Installing with percent-conda inside a running notebook can use a lot of memory while it checks for conflicts — if your notebook stalls, that's your cue to switch to the environment-dot-yaml approach instead. You also can't run apt-get with sudo in GeoLab, so anything below the Python layer needs a custom image, not a temporary environment. And pip doesn't resolve version conflicts automatically the way conda does — if something breaks, read the error message and adjust your file by hand." |
| 6:20–6:30 | Quick-reference card, four rows appearing as a simple table: `conda env list` — list environments · `conda list` — see installed packages · `conda deactivate` — leave the environment · `conda env export > environment.yml` — save what you have. | **VO:** "And if you ever want to save an environment you built on the fly, conda env export writes it back out to a file — so next time, it's one command away." |
| 6:30–6:45 | Return to split-screen diagram from earlier, now with a checkmark stamped over "Temporary Environment." On-screen text: **"One file. Any packages. Fully reproducible."** | **VO:** "One file gets you exactly the packages you need, without touching anyone else's setup — and because it's just a file, it travels with you, your students, or your collaborators." |
| 6:45–6:55 | End card: EarthScope/GeoLab lockup, URL on screen: **docs.earthscope.org/geolab**. | **VO:** "Full details are in the GeoLab docs. Build the file, run three commands, and get back to the science." |

### Production notes
- Record the terminal segments at real speed once, then speed-ramp the dependency-resolution output in editing (per the 4x note at 3:05–3:50) rather than faking it — conda's real output builds trust with a technical audience.
- Use a disposable/demo GeoLab account for all screen capture; confirm no personal file names or tokens are visible in the file browser or terminal history before publishing.
- Verify the exact commands and flags against the live docs page before final recording, since CLI syntax can drift: https://docs.earthscope.org/geolab/advanced-topics/environments/creating-temporary-environments
- Consider an on-screen callout at 4:45–5:20 reiterating that kernel selection is per-notebook — this is the detail viewers are most likely to miss and ask about afterward.
